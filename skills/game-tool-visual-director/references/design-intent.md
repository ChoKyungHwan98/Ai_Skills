# Design intent

Read this after Visual Intent and information structure are clear when the request concerns visual direction. Begin with existing screenshots, code, README, design tokens, prior decisions, and the user's references. Keep a visual choice the user already made unless it conflicts with the task; explain any proposed departure.

## Translate impressions into choices

Words such as “깔끔하게,” “고급스럽게,” or “촌스러워” describe a reaction, not an implementation. Locate what produces that reaction in the current screen before selecting a treatment. For example, “깔끔하게” may call for fewer competing priorities while retaining a dense comparison table; “고급스럽게” may call for disciplined type and consistent states rather than more effects. These are hypotheses to inspect, not preset styles.

When visual direction matters, make a short, task-specific note:

```text
Desired impression: What should the viewer sense while doing this task?
Reference traits: Which specific qualities of any reference are useful here?
Density: How much information must stay visible for the viewer's work?
Visual character: What choices should make this product recognizable and coherent?
Interaction tone: How should feedback and motion support the task?
What to avoid: Which existing or proposed choices work against that direction?
```

Consider product type, target user, usage context, desired and undesired references, and existing product constraints only when they change those answers. Extract traits from a reference, such as compact navigation or precise type hierarchy, rather than reproducing its appearance. If two plausible directions would lead to materially different work and the available context cannot resolve them, ask one focused question. Do not run a fixed interview or replace the user's chosen direction with a fashionable default.
